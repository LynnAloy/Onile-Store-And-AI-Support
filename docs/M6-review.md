# M6 审查与验收

审查范围：管理员权限、商品审核与库存、钱包智能下单授权、PST 额度、Java 结算、Vue 当前轮次协调器、Python 工具/RAG 边界，以及本地迁移部署。

## 已修正的问题

1. 库存调整只检查审核版本不足以识别期间发生的销售扣减。已增加必填 `expectedStock`，实时库存与页面读取值不一致时返回 `STOCK_CHANGED`，不覆盖新库存。
2. Java 基本类型对缺省值的处理可能把缺失库存解释为零。库存、期望库存及期望版本改为必填可空包装类型并验证；缺字段返回 400。
3. 原对话页“不会自动付款”的说明与新增授权功能冲突。已更新为钱包限额授权说明；实际 PAID 回执优先显示，已付款的原清单禁止再次载入或勾选，已完成工具卡默认折叠。
4. 自动结算若只绑定购买清单，会接受资料/授权变化后的迟到请求。现已绑定原文、当前会话、资料版本、策略版本及 5 分钟期限，结算在锁内复核。
5. 原普通环境支付禁用规则已被本需求改变。部署脚本只接受显式 M6 迁移证据，并验证目标和结构哈希；错误目标在连接数据库前被拒绝。原演示隔离、PID 归属检查和备份保护保留。

## 核心结论

- 新权限不通过普通注册授予，没有公开的升权接口。管理员身份每次在服务端核验，普通用户和两种代理凭证不能管理商品。
- 钱包默认关闭；首次启用、重新启用、提高额度必须验证支付密码，沿用五次失败锁定十五分钟。降低额度、关闭不需要密码；旧版本设置不能覆盖新设置。
- 固定 PST 日界覆盖夏季与冬季，关闭、重新登录与重新开启不清零已用额度；同用户多笔并发不突破每日额度。
- 明确的完整购买清单才可扣款，数量不能交换、推测或只成交部分商品。RX、未审核、同名规格、过期、资料变化、库存或余额不足均拒绝。
- 自动及手动付款共用同一段金融写入。失败注入后，账户、积分、库存、订单、流水、付款记录和额度都回滚。
- 一轮唯一及内容摘要防止重复扣款；未知提交结果只查询，聊天历史恢复不执行写操作。
- 收货信息由 Java 读取个人资料；模型流和自动结果仅包含必要商品及交易摘要，未传输支付密码或收货资料。

## 保留边界

当前仍是演示钱包和项目审核流程。未接入真实支付、退款、处方上传审核或药师履职。模糊症状咨询不会自主选药并扣款；自动购买目前要求完整名称与明确数量。普通环境已有药品保持原来的审核状态，需要管理员依据实际资料完成审核。

浏览器停止生成不保证撤销已经提交的自动结算；以本轮查询结果和付款订单为准。关闭授权只阻止后续未结算请求，已完成订单保留原回执。前端全量 Element Plus 包仍有构建体积提示，不影响本轮功能验收。
