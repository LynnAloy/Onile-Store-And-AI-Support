综合故障验收见[M5.1-D-validation.md](M5.1-D-validation.md)、[M5.1-D-review.md](M5.1-D-review.md)。

目标：用户将已确认资料的草稿转为待支付订单，在独立页面验证支付密码，
明确点击付款后，由Java原子完成余额、库存、订单和流水变更。
Python继续只负责AI、RAG、目录查询和获授权的草稿准备，不持有支付权限。
本阶段使用虚构商品和演示钱包；第三方支付沙箱单列M5.2。

## A阶段开始时的差距（历史背景）

- CONFIRMED只表示资料确认，没有待支付订单，不扣款、不占库存。
- 旧OrderService.submitOrder直接完成成交，已有事务、库存锁和请求键幂等，
  但不能直接等同于新的“待支付订单＋一次性支付授权”流程。
- 旧orders.status包含pending/completed/cancelled；需区分支付状态与业务展示状态，
  不能直接把历史completed全部当作经过新流程验证的PAID。
- 现有余额、流水、支付密码哈希、失败次数保护和用户锁可以复用，
  需要审查其事务回滚、锁顺序及旧接口是否可能绕过新支付边界。

## M5.1-A：冻结订单、支付状态与接口契约（首先实施，P0）

交付设计文档、机器契约、迁移方案和异常矩阵，本子阶段不实际扣款。

1. 定义payment_status：PENDING_PAYMENT → PAID或CLOSED；
   PAID不可通过取消、删除或过期回退，退款另设流程。
   草稿状态保留原义，CONFIRMED不改成“已付款”。
2. 推荐扩展现有orders及订单明细，增加来源草稿唯一关联、订单版本、支付期限、
   不可变金额/商品/收货快照和关闭原因；支付状态独立于旧status。
   同一草稿只能产生一个正式订单，更换请求键也不能重复转换。
3. 待支付期限建议15分钟；本期不预占库存，页面明确提示，付款时再检查库存。
   服务端判断到期，读取/操作路径必须拦截，不能依赖前端倒计时或定时任务及时运行。
4. 迁移只增量添加结构、索引和约束，保留现有资料与历史订单。
   历史支付标记须与流水核对，异常记录单独标识，禁止猜测补写扣款或库存。
5. 冻结下列USER接口草案及JSON结构、错误码、所有权和幂等语义：

| 接口草案 | 作用 |
| --- | --- |
| POST /api/order-drafts/{id}/checkout | 将CONFIRMED草稿转为待支付订单；Idempotency-Key与来源草稿双重防重 |
| GET /api/orders/{id} | 本人订单及支付结果恢复查询，不返回密码或授权凭证 |
| POST /api/orders/{id}/payment-authorizations | 独立验证支付密码，签发绑定此订单的一次性短期授权 |
| DELETE /api/orders/{id}/payment-authorizations | 撤销本人该订单授权；迟到响应支持定向清理 |
| POST /api/orders/{id}/pay | USER＋独立支付授权＋Idempotency-Key；用户明确提交付款 |
| POST /api/orders/{id}/close | 关闭未支付订单，与支付并发时只有一个结果 |

以上已在M5.1-B实现，完整参数以m51-payment.openapi.json为准；仅在结构校验通过的隔离演示环境启用。
正常环境保持旧流程；启用新模式时旧直接成交接口返回409，M5.1-C已接入独立付款页面。
支付授权建议使用独立请求头，绝不放进URL、模型上下文、普通聊天请求或日志。

验收：契约明确金额/版本绑定、余额不足、商品变化、授权过期、支付超时、
取消/支付并发及重复请求的处理；迁移可备份恢复；Java/Python权限表更新。

## M5.1-B：Java支付验证与原子结算（P0）

- 仅USER能从本人CONFIRMED草稿转换订单；重新校验销售资格、价格、库存、版本，
  复制已确认的私有收货快照，不接收客户端总金额覆盖，也不发送收货信息给模型。
- 一次性支付授权建议60秒以内，并受父登录会话有效期约束；数据库只存token哈希，
  绑定用户、会话、订单、订单版本、金额、币种与到期时间。
  支付密码验证成功只签发授权，不直接扣款；错误次数和锁定状态不能随失败事务回滚而消失。
- 付款事务按统一锁顺序处理用户、订单、授权与升序商品行，重新验证登录、授权、
  状态、期限、资格、审核版本、价格、库存和余额。
- 授权消费、余额扣减、库存扣减、订单PAID、支付记录、唯一流水及积分变更同事务提交；
  任一步失败全部回滚，不出现已扣款但无订单/流水的半完成状态。
- 明确业务拒绝与数据库临时失败的不同处理。价格/资格/版本冲突必须重新核对并作废授权；
  撤销或失效不能因结算事务回滚而复活。禁止在通用异常处理里重新签发授权。
- 相同请求键和相同请求只返回既有支付结果；同键不同请求冲突。
  成功重放须先识别已提交结果，不因一次性授权已消费而误报付款失败。
  不同请求键并发支付同一订单仍只能扣款一次，积分也只能发放一次。
- 保持旧读接口和模型订单查询的所有权及字段白名单。
  审查旧POST /api/orders和订单删除路径：统一结算核心及授权要求，
  不能留下直接成交绕过入口，也不能物理删除已付款流水关联记录。

验收：真实MySQL验证上述资金不变量；任意代理凭证都不能验证支付密码、签发支付授权或付款。

## M5.1-C：Vue独立付款与恢复交互（P0）

- 沿用现有简洁扁平风格：草稿核对 → 创建待支付订单 → 独立支付页。
  支付页清楚展示商品数量、金额、演示钱包标识、到期时间和“不预占库存”。
- 支付密码仅用于独立验证请求；不写localStorage、会话历史、URL或埋点。
  支付授权仅短期保存在内存，账号切换、离页、退出和撤回时清理。
- 绑定发起时的用户/会话/订单；撤回时尚未返回的授权到达后必须定向撤销，
  不得误撤销随后新授权，不得用新账号的凭证处理旧账号请求。
- 用户明确点击付款后才提交；禁止AI触发付款。
  双击防重只是交互保护，后端幂等和订单锁仍为最终保证。
- 网络中断或结果不确定时显示“正在核实付款结果”，通过本人订单接口恢复；
  不自动换请求键、换授权、重新验证密码或再次发起扣款。
- 价格/资格变化、缺货、余额不足、锁定、到期和关闭给出可执行提示；
  未知结果不能直接显示“未扣款”。

验收：桌面1366×768、450×668、390×844验证，长清单、验证弹层和付款按钮可达；
刷新、后退、切号、撤回及慢响应不会泄漏旧状态或重复支付。

## M5.1-D：真实环境验收与审查（P0）

继续使用M4.3隔离演示库、合成账号与虚构商品，原业务商品不自动审核。

| 场景 | 必须满足的结果 |
| --- | --- |
| 正常付款 | 余额/库存各扣一次；订单、支付记录、流水、积分一致 |
| 同键重放/不同键并发/双击 | 不重复扣款、扣库存或发积分 |
| 两用户竞争最后库存 | 不超卖；失败者余额与流水不变 |
| 余额不足、验证失败、锁定、过期、撤销、跨用户 | 不产生未授权资金变更 |
| 调价、审核版本变化、RX或未知资格 | 拒绝旧快照付款，要求重新核对 |
| 关闭与支付并发 | PAID/CLOSED只有一个终态，不能付款后被关闭 |
| 事务中途故障 | 无部分扣款、孤立流水或部分库存扣减 |
| 返回前断网/刷新恢复 | 查到真实最终结果，不自动再次扣款 |
| 登录退出/账号切换/授权迟到 | 旧授权不可误用，旧资料不进入新账号 |
| 所有代理角色越权 | 无法接入USER支付、授权或密码接口 |

最终交付：增量SQL、更新的Java/Python机器契约、业务与并发测试、
真实MySQL联调、登录态浏览器截图、资金一致性报告、M5.1验收/审查文档和演示脚本。
分别报告协议模拟故障与真实服务结果，不把单次成功当作可靠性证明。
