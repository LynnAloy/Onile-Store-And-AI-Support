# 购买清单交互与数量修复

日期：2026-10-27。

## 三个现象的判定

| 现象 | 判定 | 处理 |
|---|---|---|
| 枇杷露、布洛芬提示销售资格未审核 | 符合资格门禁设计；实际两商品都是 UNKNOWN/PENDING | 保留拦截，没有自动批准、改分类或伪造审核依据 |
| “加入本次草稿选择”不能勾选 | 交互缺陷：复选框错误地复用了 draftEligible 条件 | 选择与资格分离，未审核也能勾选、取消、调整数量；准备草稿按钮仍受资格/库存/数量约束，并展示原因 |
| 明确说5件、3件后仍需重新填写 | 对话到选择的结构化数据链路缺失 | 新增只读 propose_purchase，输出待核对清单并预填数量，不签发授权、不创建草稿 |

“可以选择”不等于“可以销售”，也不等于用户已经授权创建草稿。

## 数量链路

1. 用户发送“帮我下单5件枇杷露，3件布洛芬”。
2. 模型通过原生 catalog 工具查询真实商品。
3. 模型调用只读 propose_purchase：
   items[{medicineId, quantity, evidence?}]。
4. Python 检查商品确实来自本轮查询、没有重复ID，数量1–99，
   并与当前消息原文中相邻的商品名称/ID和数量对应，不能交换或凭空填写。
5. evidence 是可选原文摘录；模型不提供时仍由服务端直接检查当前消息。
   模型省略数量但原文有唯一明确数量时可恢复；原文没有数量则保留 null，不默认为1。
6. 工具结果通过原有 tool_result SSE 返回并持久化，前端预填“5、3”及待核对选择。
   回复中的清单数量由服务端直接展示，避免模型在最后一段文字中重新改写数量。
7. 用户可以调整、取消选择；只有核对后点击授权按钮，才进入既有 M4.2 指定商品授权。

多规格命中不会自动替用户选定规格，需要手动确认。
这是提取和核对辅助，不是对复杂语义的形式化证明；
有歧义时需要用户核对，模型没有成交权限。

未审核商品在清单中仍保留原数量，并明确显示阻断原因。
原有零库存、数量上限、审核资格、订单准备授权和支付边界不变。
预览阶段只提供 propose_purchase；已授权准备阶段提供 prepare_order_draft，
两种操作分阶段提供，避免重复预览代替实际准备。

## 前端变化

- 复选框仅受生成/授权进行中和最多10种选择的约束，不因未审核而禁用。
- 顶部新增当前待核对选择与阻断原因。
- 普通目录查询显式显示默认数量1；购买清单优先使用用户明确数量，
  未指定则显示待填写，不会偷偷采用默认1。
- 数量或库存不满足、资格不满足时，授权按钮禁用并显示原因，
  单商品入口也会给出错误说明，避免静默点击无反应。
- 历史显示原始清单数量，可通过“载入这份待核对清单”恢复选择；
  切换会话会清空上一会话的临时选择。

旧历史没有结构化数量结果，不会猜测回填。刷新页面并重发原句即可走新链路。
没有新增订单权限或放宽 Java 销售资格。
