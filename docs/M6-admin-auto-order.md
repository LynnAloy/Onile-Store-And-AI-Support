# 管理员与限额智能下单

目标：传统账户、库存、审核、收货及账务仍由 Java 管理；FastAPI 负责模型、只读工具调用与 RAG。浏览器连接本轮只读购买清单与 Java 的受限自动结算，不向模型提供资金凭据或收货信息。

## 使用入口

- 普通环境：`http://127.0.0.1:3000`；隔离演示：`http://127.0.0.1:13000`。
- 使用对应环境的独立管理员登录后，导航显示“药品管理”。库存调整填写原因；分类审核填写 OTC/RX、审核结果与依据。服务器保存操作者、前后值及版本，过期版本不能覆盖新修改。
- 普通环境管理员登录凭据在受保护的 `.local-run/admin-account.json`，演示管理员在 `.local-demo/admin-account.json`；随机密码不写入文档或日志。普通注册不能指定角色。
- 个人中心 → 健康钱包 → AI 智能下单：默认关闭，单笔 50.00 元，每日 200.00 元；开启、重新开启或提高任意额度需要支付密码，降低额度或关闭无需密码。
- 额度日界为 PST 固定 UTC−08:00（UTC 每日 08:00），包括夏季，不使用 `America/Los_Angeles` 的夏令时规则。
- 授权仅对当前登录有效（受现有登录过期约束）；重新登录后必须重新验证开启。关闭、重开或登录均不重置当日已用额度。
- 个人资料须有收货人、有效手机号与地址；沿用项目字段限制（15/20/50 字符），手机号按现有大陆手机号格式验证。健康档案上下文授权与钱包授权独立。

## 交易边界

默认关闭时沿用：AI 清单 → 用户授权草稿 → 独立确认资料 → 待付款 → 支付密码验证 → 手动确认付款。

开启时：浏览器以本人的 USER 凭证登记当前轮次 → FastAPI 查询真实商品并生成只读清单 → 本轮 SSE 完整结束后浏览器只提交一次结算 → Java 填写收货信息、校验并原子成交。模型不直接持有自动下单权限；AGENT_READ、AGENT_ORDER_PREPARE 均不能访问新增 USER 接口。

可自动成交的输入必须明确完整商品名及数量，例如“帮我下单5件枇杷露，3件布洛芬”。Java 再次核对原文、目录及数量，不采信模型对购买意图的判断。缺数量、多规格、同名商品、否定或假设句、未覆盖的部分清单、未审核商品、RX、缺货、余额不足、超额或资料变化均拒绝自动扣款。模糊症状咨询仍走人工核对，不据此自主选择并购买药品。

Java 在当前事务中以数据库实时价格计算金额；价格不是从模型或浏览器接收。钱包授权的是限额内按结算实时价格购买，AI 卡片价格属于快照。只有 Java 的 PAID 回执代表成交；模型生成时的“未下单”只代表其只读清单阶段。

## 一致性与权限

- 账户行锁串行化该用户的授权、资料变更、登录退出和结算。结算依次锁策略、轮次、商品（ID 升序），再写草稿、订单与支付审计。
- 当前轮次绑定用户、登录会话、会话 ID、原文摘要、钱包授权版本和资料版本，最长 5 分钟。历史清单加载仅查询结果，绝不触发结算。
- 同一轮次唯一；首次结算绑定排序后的商品与数量摘要。相同内容重放返回原结果，替换内容冲突；明确拒绝保存为终态。
- 自动与手动付款共用 `PaymentService.commitSettlement`。余额、积分、库存、订单状态、支付记录、流水与自动额度记录在同一事务提交；异常全部回滚。
- 自动订单保留独立草稿来源和支付授权审计，消费的服务器授权不发送浏览器。`auto_order_turns` 关联订单，是识别自动授权来源及累计额度的持久记录。
- 日累计仅计算当日已成功的自动订单；失败不占额度，手动付款不占 AI 额度。该阶段无退款功能，不存在通过退款自动重置额度的入口。
- 扣款提交结果不确定时返回 UNKNOWN；前端只读取同一轮次结果，不自动重发、不换键。刷新历史可恢复 PAID 回执，“付款订单”保留可核对的业务记录。
- 管理员权限每次从数据库重新检查；客户端导航不是权限依据。分类、审核通过与依据分开表达，现有商品不会被自动审核。

## 本地部署与回归

先停止对应环境，运行 `python scripts/m6_migrate.py --environment normal` 或 `demo`。脚本只接受已准备并备份过的本机数据库目标，新增前再备份，按现有 M5 SQL 补齐支付结构，保留 DDL 分步日志；MySQL DDL 不能靠事务回滚。新的结构证据绑定目标、SQL 哈希及实际建表结构，启动发现漂移拒绝启用。

恢复服务后运行 `python scripts/m6_admin.py --environment normal` 或 `demo` 创建新的独立管理员。环境启动脚本同时设置 Java 的 `COMMERCE_ENABLED` / `PAYMENTS_ENABLED` 与前端相应标志。保留旧结构及支付审计；有新付款后不得直接退回旧结算引擎。

验收使用 `CommerceBusinessTests`、`CommerceMySqlTests`、前端 `commerce.test.mjs` 与 `scripts/m6_live.py`。真实 MySQL 测试在随机临时库执行，专用数据库登录无权访问普通环境。页面联调仅使用隔离演示中的虚构账号、虚构商品及演示钱包。

该阶段是本地演示交易系统：OTC/RX 和审核字段用于项目流程，管理员仍需依据实际资料审核。支付仅为演示钱包；真实处方审核、药师履职、第三方支付与退款均未接入。
