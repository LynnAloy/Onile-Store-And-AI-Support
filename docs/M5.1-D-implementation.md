# M5.1-D：综合故障验收与恢复修复

完成日期：2026-10-28。使用固定隔离演示库、登记合成账号、虚构商品和演示余额；正常商品资格没有自动审核，正常环境保持新支付关闭。
验收结果见[M5.1-D-validation.md](M5.1-D-validation.md)，逐项审查见[M5.1-D-review.md](M5.1-D-review.md)。

## 发现并修复的恢复缺口

付款采用独立请求登记事务，再进入资金事务。进程在两者之间或资金事务中退出，可能留下REGISTERED请求。
原UI会安全地阻止重付，但没有服务端最终收敛途径，可能长期停在核实中。

新增PaymentReconciliationService与PaymentRecoveryScheduler：支付启用时每15秒检查一批最多50条、登记时间超过120秒的PAY请求。
每条请求独立事务，锁顺序与付款一致：用户→请求→订单→授权。取得锁后再次核对状态和年龄。
原结算仍在执行时，核查等待同一用户锁，不能将正在提交的付款误判为失败。
已PAID且存在唯一支付审计时，仅将请求修复为SUCCEEDED；不再扣款、发积分或生成流水。
未结算时提交REJECTED/PAYMENT_ATTEMPT_EXPIRED并撤销相关旧授权。迟到原请求读到REJECTED后终止，不能继续扣款。
到期订单同时关闭，已关闭或历史未核验订单保留相应拒绝原因。核查不修改任何余额、库存、积分或财务记录。
支付关闭时不查询支付表。未新增数据库DDL、USER接口或代理能力，也没有新增Java故障接口。

UI继续仅GET恢复未知结果，REGISTERED本身不作为未扣款证据。只有服务器已明确结束旧请求，用户才可重新验证并明确付款。
服务暂不可用时，页面保留“不要再次付款”的提示。新增错误码为409 PAYMENT_ATTEMPT_EXPIRED，outcome仍为NOT_APPLIED。
支付机器契约版本5.1.1，既有参数/六个操作兼容；平台订单规则更新为1.5并同步到两个本机SQLite索引。

## 本机故障工具及边界

m51d_fault_proxy.py只监听127.0.0.1:18181，固定上游18080。控制通过受ACL保护的本地文件，HTTP仅提供无凭据健康检查。
只能对m51c-browser.json登记账号拥有的指定订单布置一次性故障；没有通配订单、外部上游或正常数据库目标。
正常启动器无论是否存在故障文件，都直连8080。演示启动器须核对目标指纹、代理标记和运行ID才允许临时转发。
代理不记录请求/响应正文、密码或授权头，迟到撤销只记录“原身份匹配、指定授权ID”的布尔结果。
中断演示Java前核对PID命令行、工作区及demo环境标记，不能停止正常Java。

故障方式：

- 提交后丢回执：先收到Java成功响应，再关闭客户端连接；数据库确认为PAID，浏览器进入UNKNOWN，只查询原订单。
- 重启：保留Vue、数据库及代理，停止并重启演示Java；旧会话和回执可恢复，未发生新付款。
- 结算前进程退出：代理先锁住登记虚构商品行，观察请求已REGISTERED且资金事务持有用户锁后，自动终止演示Java。
  这使异常位置不依赖人工点击速度；库中没有支付记录或购买流水。恢复后真实等待120秒，由后台结束旧请求，浏览器再GET恢复。
- 迟到授权：延迟旧授权响应至新授权成功，或至另一个账号登录；原身份和authorizationId定向清理，不撤销新授权、不登出新账号。
- 迟到401：旧会话订单查询401延迟至另一个账号登录后释放，新会话继续正常查询。

另做超过15秒客户端超时的授权场景，区分“请求被客户端中止”与“旧响应在超时前真正送达”。
后者实测约1.1秒和1.6秒延迟；新授权在原清理后仍保留，后来由自身到期清理，而非被旧响应误撤销。

## 重复业务检查与账务

m51d_stress.py对每类并发跑5轮：10个同键/异键支付请求、两用户争最后库存、付款与关单竞争。
覆盖RX、UNKNOWN、PENDING、审核版本变化、价格变化、缺货、余额不足与真实PIN锁定，整批核对订单、余额、积分、库存和流水。
测试只调整本轮虚构商品；最后库存临时设1，结束恢复至先前库存减实际销量，以便最终总账仍可核对。
准备授权用后显式撤销，遵守原10个授权上限，未提高产品限额或关闭防护。

m51d_permissions.py核对两个代理角色对六个USER操作均403、跨用户404，并在最终Jar上再次执行丢回执、重启及回执重放。
m51d_audit.py在清理前只读核对登记故障账号的完整账务与旧请求/新请求状态。
真实MySQL套件另覆盖扣款后异常注入全回滚，以及恢复任务与正在结算事务竞争；应用内测试注入与独立进程退出分开报告。

## 重现顺序

先读取项目根目录的私有环境配置，禁止在命令行或聊天中传密码。以下命令仅作用于隔离演示栈：

```powershell
python scripts/m51d_fault_proxy.py start
python scripts/demo.py stop
python scripts/demo.py start
python scripts/m51c_browser_fixtures.py prepare
python scripts/m51d_fixture_order.py abort
```

从私有.local-demo/m51c-browser.json读取本轮合成账号和指定订单，登录13000。
arm使用该文件中的实际订单号，例如：

```powershell
python scripts/m51d_fault_proxy.py arm --mode abort_before_settlement --order <登记合成订单号>
python scripts/m51d_fault_proxy.py start-java
```

中断模式应先arm再在页面验证并明确付款；代理会在实际登记/锁等待出现后自动停止演示Java。
等待服务恢复和120秒阈值，再点“查询付款结果”；不得修改登记时间来替代真实等待。
看到旧请求已核实未执行后，再独立验证并明确付款一次，用于核对旧请求REJECTED与新请求SUCCEEDED。
delay_authorization可配合--release-on next_authorization或login；delay_read_unauthorized配合--release-on login。
新建测试订单会轮换合成账号会话，浏览器需重新登录；不延长旧订单或授权期限。
上述浏览器场景须分别执行，命令段不是自动完成所有页面操作的脚本；m51d_audit会拒绝缺少实际故障事件的验收记录。

```powershell
python scripts/m51d_stress.py
python scripts/m51d_permissions.py
python scripts/m51d_audit.py
python scripts/m51c_browser_fixtures.py cleanup
python scripts/demo.py stop
python scripts/m51d_fault_proxy.py stop
python scripts/demo.py start
python scripts/m51_live_smoke.py
python scripts/m51_mysql_tests.py
```

真实MySQL套件只创建临时库/受限账号并在finally清理。恢复演练只导入全新临时库，不覆盖当前付款或原业务库。
本次已清理全部登记合成数据、关闭代理并恢复标准服务；默认启动不会注入故障。
原始日志仅保留在忽略的私有目录，合成账号凭据已随清理删除；公开证据仅有合成数据聚合与截图。
